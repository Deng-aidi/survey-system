# 关键逻辑说明

本文档解释系统中六个核心逻辑模块的设计思想：跳转规则解释、填写与提交、答案校验、权限控制、**题目快照与版本链机制**、**权限隔离与跨卷统计**。所有结论均基于实际代码实现。

---

## 1. 跳转逻辑

跳转功能由 `utils/jumpResolver.js` 实现，核心思想是：**规则由后端解释执行，前端不感知任何跳转语义**。前端只需把当前题答案发给后端，后端返回 `next_question_id`，前端照单渲染。

### 1.1 condition_matches：六种 operator 语义表

跳转规则的条件形如 `{ operator, value }`，解释器支持六种 operator：

| operator | 适用题型 | 语义 | 判定方式 |
|---|---|---|---|
| `equals` | 单选 / 文本 | 答案严格等于 value | `answer === value` |
| `includes` | 多选 | 答案数组包含 value | `Array.isArray(answer) && answer.includes(value)` |
| `gte` | 数字 | 答案 ≥ value | 要求 answer 为 number，`answer >= value` |
| `lte` | 数字 | 答案 ≤ value | 要求 answer 为 number，`answer <= value` |
| `eq` | 数字 / 文本 | 严格相等（数字题专用命名） | `answer === value`，与 equals 实现相同，仅为数字题提供语义化的 operator 名 |
| `between` | 数字 | 答案落在闭区间 [min, max] | value 必须为二元数组，`value[0] <= answer <= value[1]` |

三个值得注意的防御性细节：

- **`includes` 先判 `Array.isArray`**：如果配置错误地把 `includes` 用在单选题上，answer 是字符串，`includes` 在字符串上是子串匹配，会产生意料之外的命中。显式要求数组类型，把这种配置错误的危害降为"规则永不命中"而非"规则随机命中"。
- **`gte` / `lte` 先判 `typeof answer === 'number'`**：防止字符串答案与数字 value 做隐式转换比较（如 `"25" >= 20` 在 JS 中为 true）。
- **未知 operator 返回 false**：未识别 operator 直接不命中，配合发布前校验（operator 必须在枚举内）形成双层防护。

### 1.2 为什么 resolve_next_question 返回 { matched, target } 而非裸 null

`resolve_next_question(question, answer)` 的返回值是 `{ matched: boolean, target: ObjectId | null }`，而不是简单地返回"下一题 ID 或 null"。原因是**跳转结果存在三种语义，其中两种用裸 null 无法区分**：

| 语义 | matched | target | 裸 null 方案的问题 |
|---|---|---|---|
| 命中规则，跳到指定题 | true | 目标题 _id | 可以表达 |
| 命中规则，跳到问卷结束 | true | null | 与第三种冲突 |
| 未命中任何规则，按 order 走默认下一题 | false | — | 无法表达 |

如果函数直接返回 `target`，那么"跳到结束"（target 为 null）和"无规则匹配"（也应返回 null）就混淆了。调用方无法判断：当前 null 是"该结束了"，还是"去按 order 找下一题"。拆成两个字段后，调用方的分支逻辑是完备的：

- `matched && target` → 跳到目标题；
- `matched && !target` → 问卷结束；
- `!matched` → 按 order 数组找下一题（可能也是结束）。

这个设计把**"是否命中规则"与"规则指向哪里"正交化**，是状态机表达上的常见手法：先回答"走不走规则"，再回答"规则去哪"。

另一个细节：规则按 `jump_rules` 数组顺序匹配，**第一条命中即生效**，后续规则不再评估。这让问卷创建者可以通过调整规则顺序来控制优先级，语义直观。

### 1.3 发布前校验三项

跳转规则在配置阶段（Q2 接口）只做存在性校验，完整校验推迟到发布时（S5 接口，`PATCH /status` 置为 open 时）统一执行。原因是：配置过程中问卷处于中间态，强制校验会让正常的分步配置无法保存——比如先配置"Q1 跳到 Q3"，再添加 Q3，配置瞬间 Q3 尚不存在。

发布时的完整校验包含三项，全部通过才允许置为 open，否则返回 422 并逐条列出错误：

**① 引用存在性**：每条规则的 `targetQuestionId` 必须是本问卷某道题的 `_id`，或为 null（跳到结束）。防止指向已删除题目的"幽灵跳转"。

**② 只允许向前**：目标题的 `order` 必须严格大于当前题的 `order`，不允许回跳。这一约束把跳转图限定为**有向无环图的结构基础**——回跳是填写流程死循环的最主要来源，直接在规则层禁掉。

**③ DFS 环检测**：即使只允许向前，仍需防御性环检测。校验算法先建邻接表：节点为题目，边包括两类——每条 jump_rule 的 current → target（target 为 null 指向虚拟终点，不建边），以及**默认边**（未命中规则时按 order 走向下一题）。然后从 order 最小的题出发做 DFS，路径上再次遇到已访问节点即判环。

为什么要把默认边也纳入图？因为环可能由"规则边 + 默认边"混合构成：例如 Q1 配规则跳到 Q3，Q3 无规则，默认顺序走到 Q4——若 Q4 再有办法回到 Q1（虽然被 ② 禁止，但双重防护），仅靠 ② 无法覆盖所有理论路径。把默认边纳入图后，检测的是**填写者实际可能走出的完整状态空间**，而非仅规则定义的边。

## 2. 填写与提交逻辑（重点）

填写流程由三个接口构成：F1（取问卷）、F2（单题校验+跳转解释）、F3（提交落库）。核心设计是**"交互期无状态，提交期全量重放"**。

### 2.1 F1/F2 的无状态设计

**F1（GET /api/surveys/by-token/:token）** 只做一件事：返回问卷结构（题目、选项、跳转规则、版本号 `__v`）。它不在服务端创建任何"填写会话"，不写数据库。

**F2（POST .../answers/validate）** 接收 `{ question_id, answer }`，做两件事：用 `validateAnswer` 校验单题合法性；合法则用 `resolve_next_question` 解释跳转，返回 `next_question_id`。它同样不写数据库，校验失败也返回 200（仅响应体 `valid: false`），因为"答案不合法"是业务结果而非传输错误。

这种设计的收益：

- **服务端零会话状态**：不需要在内存或数据库里维护"某用户填到第几题"，天然支持水平扩展，任意请求打到任意实例都能正确处理。
- **状态由前端持有**：前端维护本地 `answers` 数组（只存校验通过的答案），按后端返回的 `next_question_id` 前进。刷新页面会丢失进度——这是有意的取舍，本系统面向短问卷场景，用实现简单性换取了会话恢复的复杂度。
- **校验规则单点维护**：所有校验逻辑在 `validateAnswer` 一处，F2 用它做即时反馈，F3 用它做落库前复检，两处永远一致。

### 2.2 F3 的重放路径二次校验

F3（POST .../submissions）是落库关口。它不信任前端提交的 answers 的"完整性"，而是**在服务端用同一套跳转解释器重放整个填写过程**，逐步重建"本应走的路径"，再核对提交是否与之吻合。

完整流程（代码在 routes/fill.js 的 F3 路由）：

1. **格式检查**：answers 必须是数组；每项必须有字符串 question_id 和已定义的 answer；不允许重复 question_id。
2. **版本冲突检查**：前端提交时携带 `expected_version`（即 F1 返回时的 `__v`）。若与当前问卷 `__v` 不一致，说明填写期间问卷被修改过，返回 409 要求刷新重填。这是乐观锁，防止按旧结构填写的数据污染新结构。
3. **归属检查**：提交的每个 question_id 必须属于当前问卷，否则 409（问卷可能已被修改）。
4. **重放路径**：从 order 最小的题开始，模拟填写过程：
   - 当前题有答案 → 用 `validateAnswer` 二次校验（防绕过 F2 的伪造提交），然后 `resolve_next_question` 解释跳转：命中规则跳到目标题（null 则路径结束），未命中按 order 前进；
   - 当前题无答案 → 若为必答题，记入错误；然后按 order 前进；
   - 重放中检测跳转目标不存在、路径成环，立即报错中止（防御 draft 期遗留的非法规则）。
5. **路径外检查**：提交的答案若包含重放路径未经过的题目，记入错误（说明前端状态与问卷结构不一致）。
6. **有任何错误 → 400 FINAL_VALIDATION_FAILED**，逐条返回；全部通过 → 写入 submission 文档。

### 2.3 具体例子：为什么"检查必答是否在 answers 里"是错的

设一份问卷：Q1（单选，必答，选项 A/B）→ Q2（文本，必答）→ Q3（数字，必答）。Q1 配置了跳转规则：选 A → 跳到结束。

**情形一：填写者 Q1 选 A。** 按规则路径直接结束，Q2、Q3 从未被渲染，answers 里只有 Q1。提交时重放路径为 [Q1]，Q2/Q3 不在路径上，它们的必答约束不生效 → **不报错，正确落库**。

如果采用朴素的"检查所有必答题是否都在 answers 里"策略，这份完全合法的提交会被误判为"漏答 Q2/Q3"而拒绝——**误伤了被跳转合法绕过的必答题**。这就是必须重放路径的根本原因：必答约束的作用域是"填写者实际经过的路径"，不是"问卷的全部题目"。

**情形二：填写者 Q1 选 B（未命中规则），走默认顺序，但漏答了 Q3。** 重放路径为 [Q1, Q2, Q3]。重放到 Q3 时发现无答案且必答 → 记入错误 → 返回 400，错误信息明确指出 Q3 未作答。**该拦的拦住了**。

两个情形对比可见：重放机制精确区分了"被规则绕过"与"应答未答"，这是任何静态检查（如提交前遍历必答列表）都无法做到的，因为只有动态执行跳转规则，才能知道路径的真实形状。

### 2.4 二次校验的必要性

有人会问：F2 已经逐题校验过，F3 为何再校验一遍？因为 F2 的信任边界只在单次请求内。恶意客户端完全可以跳过 F2 直接构造 F3 请求体。F3 的重放把每一道题的校验、每一次跳转的解释都在服务端重新执行，前端只是"建议"，后端才是"裁决"。这是典型的**客户端不可信原则**在表单场景下的落地。

## 3. 校验逻辑

`validateAnswer(question, answer)` 是所有答案校验的唯一入口，规则按题型分派。

### 3.1 空答案判定（先于题型分派）

空答案的判定是统一的四选一：`undefined`、`null`、去除首尾空白后为空串的字符串、空数组。判定为空的后果取决于 `required`：

- 必答题 → 直接报错"本题必答"，不再做题型校验；
- 非必答题 → 立即通过，不再做题型校验（空答案对非必答题即"跳过"，合法）。

把空判定前置有两个好处：一是避免后续分派逻辑对 null/空数组做无意义的类型检查；二是统一了"未作答"的语义边界，防止不同题型对"空"的定义漂移（比如文本题把 `""` 当合法空答案而数字题报错）。

### 3.2 四种题型的校验规则表

| 题型 | 类型检查 | 值域检查 |
|---|---|---|
| single_choice | answer 必须是字符串 | 必须等于 options 中某个 value（不在选项范围内即拒绝，防伪造选项值） |
| multiple_choice | answer 必须是数组，每个元素必须是字符串 | 每个元素必须在 options value 范围内；不允许重复值；`min_choices` / `max_choices` 约束数组长度 |
| text | answer 必须是字符串 | `min_length` / `max_length` 约束字符数 |
| number | answer 必须是有限数值（`Number.isFinite`，拒绝 NaN/Infinity） | `integer: true` 时必须是整数；`min` / `max` 约束取值范围 |

值得注意的边界处理：

- **数字题拒绝非有限数**：JSON 虽然无法传输 Infinity/NaN，但 `validateAnswer` 也用 `Number.isFinite` 兜底，防御通过其他途径（如脚本直接调用）传入的异常值。
- **多选题查重**：`["a", "a"]` 会被拒绝，防止客户端 Bug 或构造请求造成选项计数虚高——这与统计模块的"一次 unwind 一票"语义直接相关。
- **unknown 题型兜底报错**：数据库里若出现四种之外的 type（如历史遗留数据），校验直接失败而非静默通过，异常显性化。

## 4. 权限控制

系统存在两类访问主体：问卷创建者（管理侧）与填写者（公开链接侧），分别对应两套鉴权策略。

### 4.1 创建者鉴权：为什么用 creator_id.equals() 而非 ===

管理侧接口（问卷 CRUD、题目配置、发布、统计）统一串两个中间件：`authenticate`（验 JWT，挂 `req.user`）+ `requireSurveyOwner`（查 survey，比对归属）。

归属比对的代码是 `survey.creator_id.equals(req.user._id)`，而不是 `survey.creator_id === req.user._id` 或 `survey.creator_id.toString() === req.user._id`。原因是类型不对称：

- `survey.creator_id` 是 Mongoose 文档字段，类型为 **ObjectId 对象**；
- `req.user._id` 来自 JWT payload，签发时已显式 `toString()`，类型为**字符串**。

`===` 对对象比较的是引用，ObjectId 对象与字符串永远不相等——用 `===` 会导致**任何创建者都无法操作自己的问卷**，是一个必然触发但容易被测试漏掉的 Bug（手工测试若只用一个账号，很难发现归属判断恒为 false，因为测试者往往同时怀疑是 token 问题）。`.equals()` 是 Mongoose ObjectId 提供的类型安全比较方法，内部会自动处理字符串与 ObjectId 的互转，语义明确。

另一个细节：surveyId 参数若非法（非 ObjectId 格式），`findById` 会抛 `CastError`，中间件将其捕获并按 404 处理而非 500——非法 ID 语义上就是"不存在这样的问卷"。

### 4.2 填写端 optionalAuth 的三种状态

填写侧接口（F1/F2/F3）使用 `optionalAuth` 而非强制鉴权，因为问卷可能允许匿名填写。这个中间件把请求分为三种状态：

| 状态 | 条件 | req.user | 后续行为 |
|---|---|---|---|
| 无 Authorization 头 | 未携带 token | 不挂载 | 按匿名处理，放行 |
| token 有效 | 验签通过 | 挂载 { _id, username } | 按登录用户处理，F3 落库时记录 user_id |
| token 无效/过期 | 验签失败 | 不挂载 | **按匿名放行**，不在中间件报错 |

第三种状态是关键设计：token 失效不阻断请求。理由是职责分离——"请求者是谁"与"问卷接不接受匿名"是两个独立判断。如果在 optionalAuth 里对失效 token 返回 401，那么所有匿名问卷对"本地存了过期 token 的用户"会意外拒绝访问。中间件只负责"尽可能识别身份"，把"身份是否足够"的决策留给路由层：F1 的 `loadAccessibleSurvey` 会检查 `allow_anonymous === false && !req.user`，此时才返回 401 `LOGIN_REQUIRED`。

这样，匿名问卷对三种状态全部开放（登录用户的提交会带上 user_id，便于溯源）；非匿名问卷对后两种状态中的第一种（无 token）和第三种（token 失效）统一拒绝，行为一致且可预期。

## 5. 题目快照与版本链机制（第二阶段新增）

第二阶段的核心设计：**问卷里的题是题库题的物化快照**，而不是引用指针。题库题独立成 `questions` 集合，承载版本链与共享语义；问卷继续持有 `questions[]` 内嵌数组，但新增快照来源字段。

### 5.1 快照生成流程

从题库加入问卷时，后端 `POST /api/surveys/:surveyId/questions/from-library` 执行：

1. **读权限校验**：目标题库题的可读范围 = 创建者 ∪ `is_shared=true` ∪ `shared_with` 含当前用户。无权限返回 403 QUESTION_NOT_ACCESSIBLE。
2. **同卷重复拦截**：问卷 `questions[]` 中已有 `source_question_id === question_id` 时返回 400 DUPLICATE_QUESTION。不同版本（v1 vs v2）允许同时加入，因为快照来源不同。
3. **深拷贝题面**：复制 `type / title / options / validation`，选项 `_id` 重新生成，`value` 原样保留（统计口径依赖它）。
4. **写入快照字段**：新题 `_id` 是本地生成的 ObjectId（与题库题 `_id` 不同），`source_question_id / source_version / snapshot_at` 自动填充，`schema_hash` 由 `utils/schemaHash.computeSchemaHash` 计算。
5. **保存并重排**：`save()` 保证 `__v` 递增，`order` 自动设为数组长度。

为什么快照必须是物化深拷贝？**改题库不影响已发布问卷与旧答卷**。题库题的 `options[]` 在 v2 可能被修改，但已发布问卷里的 v1 快照是独立文档，答卷 `answers[].question_id` 指向快照本地 `_id`，归属永不丢失。

### 5.2 追加式版本链

题库题的版本链由三个字段维护：

| 字段 | 含义 | 规则 |
|---|---|---|
| `root_id` | 链根节点 | 首个版本的 `root_id = 自身 _id`；后续版本继承根节点 |
| `parent_id` | 上一版本 | 根版本为 null；新版本 `parent_id = 被派生版本 _id` |
| `version` | 链内序号 | 从 1 递增 |

任何修改都**生成新文档**，旧版本文档永不 UPDATE / DELETE。并发创建新版本时，`{root_id, version}` 唯一索引捕获 E11000，应用层 `createNextVersion` 最多重试 1 次。

**恢复旧版不是回滚**：`POST /restore` 用旧版内容再生成一个新版本（`parent_id` 指向链尾），历史保持线性。

### 5.3 题库题刻意不存三个字段

| 字段 | 原因 |
|---|---|
| `order` | 属于"在某份问卷里的位置"，跨问卷无意义 |
| `required` | 属于"在某份问卷里是否必答"，跨问卷无意义 |
| `jump_rules` | 规则的 `targetQuestionId` 引用问卷内本地题的 `_id`，跨问卷无意义 |

结论：题库承载**题面语义**，问卷承载**编排语义**。改题必须走 `POST /versions`（生成新版本），原地 PATCH 结构字段返回 400 QUESTION_STRUCTURE_IMMUTABLE。

## 6. 权限隔离与跨卷统计（第二阶段新增）

### 6.1 structureLock：结构锁定的双层拦截

中间件 `middleware/structureLock.js` 在四个结构变更端点（加题 `POST /questions`、改跳转 `PATCH /jump_rules`、从题库加 `POST /from-library`、删题 `DELETE /questions/:qid`）之前执行。判定条件：

```js
isStructureLocked = !!survey.published_at || survey.status !== 'draft'
```

- `published_at` 是首次发布时间，只写不清。draft → open 时写入；之后任何状态变更都不清零；
- `status !== 'draft'` 覆盖第一阶段没有 `published_at` 的旧数据（旧问卷 status 已是 open/closed）；
- 已发布过的问卷**不能再回退 draft**：`PATCH /status` 中，若 `status === 'draft' && req.survey.published_at`，返回 409 CANNOT_REVERT_TO_DRAFT。

前端同步配合：只读时隐藏发布/从题库/添加表单按钮，禁用 `#e-deadline` 与 `#btn-save-settings`，显示提示"问卷已发布/已锁定，题目与结构不可修改"。但 `PATCH /api/surveys/:surveyId`（元信息：标题/说明/截止时间）后端仍允许修改——结构锁定只作用于结构端点。

### 6.2 跨卷统计的三层隔离

跨卷统计 `GET /api/questions/:questionId/stats` 有三层隔离机制：

**① 权限隔离（谁能查）**：仅创建者可调用（即使他人是共享对象，也能看到题库题内容，但不能查统计）。这是有意的收紧——共享语义下不应让创建者看到别人的答卷数据。

**② 范围隔离（统计哪些问卷）**：反查 `{'questions.source_question_id': {$in: versionIds}}` 后，遍历结果按 `creator_id === 当前用户` 过滤。他人问卷（无论是否匿名）全部剔除，计入 `excluded_surveys_count`。

**③ 结构隔离（如何分组）**：按 `schema_hash` 分组而非按 `source_question_id` 分组。`schema_hash` 是 `type + options + validation` 规范化排序后的 MD5 指纹。同根题的不同快照可能有不同题面（draft 期允许本地改写），用 hash 分组让：

- 相同结构的快照答案合并统计；
- 不同结构的快照独立成组（`by_schema_group` 数组返回，每组带 `representative_version`）；
- 本地改写不会污染原始题库题的统计口径。

### 6.3 多版本同卷答案不丢失

同一问卷可能同时引用了同一题库题的多个版本（v1 和 v2）。早期实现只取 `hits[0]` 导致第二个版本的答案丢失。现在改为收集**所有命中快照**到 `surveyBuckets`，按 `survey_id` 合并：

- `answer_count` 用 `countDocuments({ survey_id, answers.question_id: { $in: allLocalIds } })`，按提交文档计数（同一人同时答了 v1 和 v2 只算 1 人）；
- `option_counts` 用全部命中 `localIds` 做 `$in` 查询，两个版本的答案合并进选项计数（不遗漏）；
- 问卷条目增加 `source_versions: [1, 2]` 数组，前端可显示"v1、v2"。

### 6.4 统计口径的诚实性

文档必须诚实记录：需求文案写"跨卷统计汇聚所有引用这道题的问卷数据"，但实际实现只统计**创建者自己的问卷**。理由：共享语义下，创建者不应该知道别人填了什么。答辩时主动说明这一取舍，比让老师在代码里发现口径偏差好得多。
