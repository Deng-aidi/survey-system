# 数据库设计说明

## 1. 为什么选 MongoDB 而非关系型数据库

本系统采用 MongoDB 作为持久化层，核心原因并非"非关系不可"，而是问卷业务天然具有**多态结构、频繁嵌套、聚合导向**三大特征，与文档型数据库的模型高度契合。以下从四个维度与关系型建表方式做对比。

### 1.1 Schema 灵活性：题型差异导致字段多态

问卷中的题目并非同构记录。单选题需要 `options[]`（标签+值成对），文本题需要 `min_length/max_length`，数字题需要 `min/max/integer`。若用关系型数据库，通常有两种做法：

- **宽表方案**：一张 `questions` 表包含所有可能字段（`min_length`、`max`、`option_a_label`…），大量列为 NULL，违背第一范式，且新增题型时必须改表结构。
- **EAV（实体-属性-值）方案**：`question_attributes` 行存储键值对，查询时需要多次自连接或行转列，统计时写起来极其繁琐。

MongoDB 的 **Schema 子文档**允许同一数组内的元素拥有不同结构：`single_choice` 题自带 `options[]`，`text` 题自带 `validation.min_length`，互不干扰。新增题型时只需在应用层扩展枚举值，无需迁移数据库。

### 1.2 嵌套题目结构：一次读取即可渲染整卷

关系型做法通常将题目独立成表，通过 `survey_id` 外键关联。渲染问卷编辑器或填写页时，需要执行：

```sql
SELECT * FROM surveys WHERE id = ?;
SELECT * FROM questions WHERE survey_id = ? ORDER BY order;
SELECT * FROM options WHERE question_id IN (...);
SELECT * FROM jump_rules WHERE question_id IN (...);
```

至少 4 次查询或 3 次 JOIN。MongoDB 将 `questions[]`、`options[]`、`jump_rules[]` 全部嵌入 Survey 文档，**`findOne` 即可原子地取回整卷**，消除了 N+1 和 JOIN 开销。

### 1.3 跳转规则可配置：图结构天然适合嵌入

跳转规则是问卷的核心差异化功能。每道题可以配置多条 `jump_rules`，每条规则包含 `condition.operator + value` 与 `targetQuestionId`。关系型数据库需要额外的 `jump_rules` 表，并通过 `question_id → target_question_id` 自引用外键维护。当题目增删时，需要级联更新或软删除，引用完整性维护成本高。

MongoDB 将 `jump_rules` 作为 `questions[]` 子文档的内嵌数组，**题目与规则同生同灭**：删除题目时，其跳转规则随子文档一并消失，无需额外级联操作。同时，发布前的环检测算法直接在内存中的嵌套对象上运行 DFS，避免了跨表遍历。

### 1.4 聚合统计：管道天然支持数组展开

统计模块需要对 submissions 中的 answers 做按题分组、选项计数、平均值计算。关系型做法需要：

```sql
-- 单题选项统计
SELECT answer, COUNT(*) FROM answers
WHERE question_id = ? AND survey_id = ?
GROUP BY answer;
```

若 answers 按 `question_id` 分表，则跨题统计更复杂。MongoDB 的 **Aggregation Pipeline** 允许直接 `$unwind: '$answers'` 展开内嵌数组，随后 `$match`、`$group` 一气呵成。单选题一次 `$unwind` 即可分组；多选题答案本身是数组，二次 `$unwind` 将每个选中值拆成独立行再计数。这种"数组即集合"的语义在关系型中极难优雅表达。

## 2. 集合划分

系统划分为三个核心集合：

| 集合 | 职责 | 拆分理由 |
|---|---|---|
| `users` | 用户注册信息（用户名、密码哈希、创建时间） | 用户是独立实体，与问卷为一对多关系；密码字段需 `select: false` 隔离 |
| `surveys` | 问卷元信息 + 题目嵌套数组 + 跳转规则 | 问卷与其题目为**强归属、同生命周期**关系，嵌入可保证原子读写 |
| `submissions` | 填写记录（问卷 ID、用户 ID、起止时间、答案数组） | 与 survey 为一对多关系，数据量随填写次数线性增长，独立集合避免 survey 文档膨胀 |

**为什么 submissions 不嵌入 surveys？** 如果每填一次都往 survey 文档里 append，`submissions` 数组会无限膨胀，很快逼近 16 MB 文档上限。更重要的是，统计查询通常只读 submissions，不需要同时带回 survey 的完整题目结构。分离后，统计管道可以只扫描 submissions 集合，survey 只做轻量级关联。

## 3. Schema 详细设计

### 3.1 users 集合

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `_id` | ObjectId | 是 | 自动生成 | 主键 |
| `username` | String | 是 | — | 唯一，trim，长度 2–32 |
| `password` | String | 是 | — | bcrypt 哈希，默认查询不返回（`select: false`），长度约束作用于原始输入 |
| `created_at` | Date | 是 | `Date.now` | 不可变（`immutable: true`） |

模型关闭 `versionKey`，用户文档不涉及并发数组操作，无需乐观锁。

### 3.2 surveys 集合

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `_id` | ObjectId | 是 | 自动生成 | 主键 |
| `url_token` | String | 是 | 随机生成 | 问卷公开链接标识，全局唯一 |
| `creator_id` | ObjectId | 是 | — | 指向 users._id，创建者 |
| `title` | String | 是 | — | 问卷标题，trim，最长 100 字符 |
| `description` | String | 否 | `''` | 说明，最长 1000 字符 |
| `status` | String | 是 | `'draft'` | 枚举：draft / open / closed |
| `allow_anonymous` | Boolean | 是 | `false` | 是否允许未登录用户填写 |
| `deadline` | Date | 否 | `null` | 截止时间，null 表示不限 |
| `questions` | Array | 是 | `[]` | 题目子文档数组，见下表 |
| `created_at` | Date | 是 | 自动生成 | Mongoose `timestamps` 生成 |
| `updated_at` | Date | 是 | 自动生成 | 同上 |
| `__v` | Number | 是 | `0` | Mongoose 乐观锁版本号 |

#### questions[] 内嵌子文档

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `_id` | ObjectId | 是 | 自动生成 | 子文档主键，用于跳转规则引用 |
| `type` | String | 是 | — | 枚举：single_choice / multiple_choice / text / number |
| `title` | String | 是 | — | 题干，最长 200 字符 |
| `order` | Number | 是 | `0` | 显示顺序，决定默认下一题 |
| `required` | Boolean | 是 | `false` | 是否必答 |
| `options` | Array | 视题型 | `[]` | 选项子文档数组，仅 choice 题型有效 |
| `validation` | Mixed | 否 | `{}` | 校验规则，按题型存储不同字段 |
| `jump_rules` | Array | 否 | `[]` | 跳转规则子文档数组 |

#### options[] 内嵌子文档

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | ObjectId | 是 | 子文档主键 |
| `label` | String | 是 | 选项显示文本 |
| `value` | String | 是 | 选项提交值，同一题内唯一 |

#### jump_rules[] 内嵌子文档

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `condition.operator` | String | 是 | 枚举：equals / includes / gte / lte / eq / between |
| `condition.value` | Mixed | 是 | 比较值，视 operator 可为字符串、数字或二元数组 |
| `targetQuestionId` | ObjectId | 否 | 目标题目 `_id`；`null` 表示跳到问卷结束 |

### 3.3 submissions 集合

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | ObjectId | 是 | 主键 |
| `survey_id` | ObjectId | 是 | 指向 surveys._id |
| `user_id` | ObjectId | 否 | 填写者；匿名时为 `null` |
| `started_at` | Date | 是 | 开始时间（当前实现中与 submitted_at 相同） |
| `submitted_at` | Date | 是 | 提交时间 |
| `answers` | Array | 是 | 答案子文档数组，见下表 |

#### answers[] 内嵌子文档

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `question_id` | ObjectId | 是 | 题目 ID |
| `question_type` | String | 是 | 冗余存储题型，**消除统计时的 JOIN** |
| `answer` | Mixed | 是 | 答案值，四种形态见下节 |

## 4. 核心设计权衡

### 4.1 题目嵌入 surveys 而非独立集合

将 `questions` 作为 surveys 的内嵌数组，而非独立 collection，是系统最重要的 schema 决策之一。支撑这一决策的论据至少包括以下四条：

**① 读性能：整卷原子读取**
问卷的读取场景（编辑器加载、填写页加载、发布前校验）都需要**同时获得元信息和全部题目**。如果题目独立存储，即使做了外键索引，也无法避免多次往返或 JOIN。嵌入后，所有与问卷相关的读取操作退化为单次 `findOne`，在 MongoDB 的 WiredTiger 缓存内即可完成，I/O 成本最低。

**② 写原子性：题目增删与版本号同步**
添加题目时，需要同时更新 `questions` 数组并递增 `__v`（乐观锁）。如果题目独立 collection，需要分布式事务或两阶段提交来保证"题目插入 + survey.__v 递增"的原子性。嵌入后，Mongoose 的 `save()` 天然保证两者在同一文档、同一次写操作中完成，无需事务。

**③ jump_rules 的引用完整性**
跳转规则通过 `targetQuestionId` 引用同卷其他题目的 `_id`。如果题目独立 collection，删除一道被引用的题目后，需要额外维护引用完整性（如触发器或应用层补偿），否则跳转规则会指向幽灵题目。嵌入后，题目与规则同生同灭：删除 survey 文档时，其全部题目及跳转规则一并消失；删除单道题目时（通过 `$pull` 或 `splice`），Mongoose 也会正确处理子文档引用失效问题。

**④ 代码复杂度：避免跨集合事务**
Node.js + Mongoose 的多集合事务需要 replica set 环境，且代码复杂度显著上升（`session.startTransaction`、`commitTransaction`、`abortTransaction`）。嵌入方案将问卷相关的所有 CRUD 收敛到单一文档，应用层无需处理事务边界，大大降低了并发 Bug 的风险。

### 4.2 answers 冗余 question_type 的理由：统计零 JOIN

在 `submissions.answers[]` 中，每道答案除了 `question_id` 和 `answer` 外，还冗余存储了 `question_type`。

为什么这样做？因为统计模块（T1/T2）需要按题型决定聚合策略：
- `single_choice` / `multiple_choice` → 按选项值分组计数；
- `number` → 计算 avg / min / max；
- `text` → 收集所有文本值。

如果不冗余 `question_type`，统计管道需要先 `$lookup` surveys 集合，再展开 `questions[]` 数组找到对应题目，才能知道题型。在 MongoDB 中，**`$lookup` 后展开数组会显著增加管道复杂度和内存占用**。冗余 `question_type` 后，统计管道完全在 submissions 集合内闭环运行：先 `$match` survey_id，`$unwind` answers，`$match` question_id，然后直接按 `question_type` 分支处理。**统计查询零 JOIN**，既提升了性能，也保证了统计逻辑在代码层面的局部性。

代价是存储空间增加（每个答案多一个短字符串字段），但在现代 SSD 上，这种冗余属于典型的**以空间换时间**策略，收益远大于成本。

### 4.3 answer 使用 Mixed 类型的四种形态

`answers.answer` 字段声明为 `Mixed` 类型，因为不同题型的答案形态差异巨大：

| 题型 | 形态 | 示例 |
|---|---|---|
| single_choice | String | `"male"` |
| multiple_choice | String[] | `["apple", "banana"]` |
| text | String | `"good product"` |
| number | Number | `25` |

如果使用强类型约束（如固定为 String），数字题需要序列化为字符串再反序列化，多选题需要 JSON 序列化，增加了无谓的转换层。`Mixed` 允许直接存储原生 JSON 类型，与前端表单控件（radio / checkbox / textarea / number input）的形态一一对应，减少了类型失真。

同时，`Mixed` 的"弱类型"风险由应用层严格校验兜底：`validateAnswer` 函数在 F2/F3 阶段会对每种题型的 answer 做类型和范围检查，确保落库的数据始终符合预期。

## 5. 索引设计

### 5.1 users

| 索引字段 | 类型 | 支撑查询 |
|---|---|---|
| `username` | 唯一索引 | 登录时按用户名查找；注册时判重。由 Schema `unique: true` 自动创建 |

### 5.2 surveys

| 索引字段 | 类型 | 支撑查询 |
|---|---|---|
| `url_token` | 唯一索引 | F1 填写端按 token 查问卷；分享链接解析。由 Schema `unique: true` 自动创建 |
| `creator_id` | 单字段索引 | GET /api/surveys 列表按创建者过滤 |
| `status` | 单字段索引 | 按状态过滤（如仅展示 open 问卷） |
| `creator_id + status` | 复合索引 | 列表页常见的"我的草稿"或"我的已发布"联合过滤，避免索引交集 |

**为什么没有给 `questions._id` 建索引？** `questions` 是内嵌数组，`questions._id` 的查找发生在已加载的 survey 文档内存中（`questions.find(q => q._id.toString() === ...)`），不需要数据库索引支撑。MongoDB 对子文档 `_id` 不会自动建独立索引。

### 5.3 submissions

| 索引字段 | 类型 | 支撑查询 |
|---|---|---|
| `_id` | 默认主键索引 | 所有集合自带 |

**当前未显式定义其他索引**，属于已知优化空间。实际运行中，统计管道频繁使用 `{ survey_id: ..., 'answers.question_id': ... }` 作为 `$match` 阶段，若数据量增大，建议补充以下索引：

- `survey_id` 单字段索引：支撑按问卷过滤 submissions；
- `survey_id + 'answers.question_id'` 复合索引：支撑统计管道前置过滤，减少 `$unwind` 前的扫描量。

由于当前测试数据量较小，未建索引时聚合性能仍可接受，但生产环境应补充。

## 6. 已知限制

### 6.1 16 MB 单文档上限的量级估算

MongoDB 单文档上限为 16 MB。估算各集合的文档体积：

- **Survey 文档**：每道题约 300–500 字节（含题干、选项、跳转规则）。100 道题约 50 KB，距离 16 MB 有 **300 倍余量**。即使包含大量长文本描述，通常也不超过 1 MB。
- **Submission 文档**：每道答案约 100 字节（question_id + question_type + answer）。1000 道答案约 100 KB，距离 16 MB 有 **160 倍余量**。

结论：在常规问卷规模（数十题、数千份提交）下，16 MB 上限不构成实际约束。极端场景（如每份问卷含上万道题）需要拆分题目为独立集合，但本系统面向普通调研场景，当前设计完全够用。

### 6.2 __v 的良性特性

Survey 文档保留了 Mongoose 默认的 `__v` 字段，作为乐观锁版本号。其关键特性在于：**`__v` 的递增是单调且不可回退的**，这使其非常适合防范并发修改导致的路径不一致。

具体来说，当用户 A 正在填写问卷时，创建者 B 修改了题目结构（增删题、调整跳转规则）并保存，`__v` 随之递增。用户 A 提交时携带的 `expected_version` 与当前 `__v` 不一致，后端返回 409 `SURVEY_CONFLICT`，提示刷新重填。这一机制不需要额外的时间戳或全局锁，实现轻量且可靠。

虽然 `save()` 对任何字段修改都会递增 `__v`（包括 title 等元信息），但这对业务是**良性**的：元信息变更虽然不会直接影响答题路径，但 `__v` 的单调递增保证了"任何并发修改都能被检测到"，不会出现 A 填写旧版问卷却被静默接受的情况。如果未来需要区分"结构变更"与"元信息变更"，可以引入独立的 `structure_version` 字段，但当前单一 `__v` 已满足需求。
